# `snapshot()` is computed by page JavaScript, not BiDi's accessibility locator

Agents need a compact list of a page's controls (browser-harness reads Chrome's accessibility tree). BiDi's `browsingContext.locateNodes` with an `accessibility` locator hangs in Zen, and Firefox exposes no accessibility tree over BiDi. So `snapshot()` walks the DOM, including open shadow roots, in injected JS. It derives a role and accessible name for each visible interactive element and tags it with a `data-zh-ref` attribute. Every selector-taking helper accepts that ref (`"@e3"`). Iframes are included: Python runs the same JS in each visible child frame's own browsing context (the walk returns frame `contentWindow`s, which BiDi serializes as context ids, so cross-origin frames work), numbers them `f1`, `f2`… and tags their elements `f1e3`. The frame-number → context map lives on the top window (`window.__zhFrames`), so it dies with the page like the refs do; ref-taking helpers run their lookup in that context and send pointer and key actions to it with frame coordinates, since top-level input does not reach cross-origin frames. A GitHub repo page comes out at ~100 lines (~750 tokens) against ~58k tokens of HTML.
